# Invoice Desk: from PDF to decision

**Case study:** AI Solutions Analyst, Problem Statement 1 (Finance / AP).
A working process that takes a vendor invoice (PDF, scan or image) and returns a reasoned decision: **Approved, Needs review, On hold or Rejected**. It shows every stage live, and a dashboard keeps the history.

## Run it

Requires Python 3.10+, `pdftotext` / `pdftoppm` (poppler) and `tesseract`.

```bash
# macOS:  brew install poppler tesseract
# Debian: sudo apt install poppler-utils tesseract-ocr
pip install -r requirements.txt
python app.py                       # http://localhost:5000
```

Or with Docker: `docker build -t invoice-desk . && docker run -p 8000:8000 invoice-desk`

Then:

1. Open the app, click **Reset demo data**, then **Run all in order**, or click the samples one at a time.
2. Drag in any PDF or image of your own to run it through the same process.
3. Open **Dashboard** for history, outcome mix and per-run traces, and **Purchase orders** for live PO balances.

Run the checks from the command line: `python scripts/test_pipeline.py -v`. It runs all 11 samples against a throw-away database and asserts each decision.
Regenerate the sample invoices and PO data (dates are relative to today): `python scripts/generate_samples.py`.

## What it does

| # | Stage | What happens |
|---|---|---|
| 1 | Receive | Hash the file, count pages |
| 2 | Read | Use the PDF text layer, or fall back to OCR and record its confidence |
| 3 | Extract | Vendor, invoice #, date, PO ref, currency, subtotal, tax, total, line items. Every value keeps its source line and a confidence. Embedded tax is backed out |
| 4 | Completeness | Missing critical fields put the invoice on hold, with a precise request per gap |
| 5 | Vendor | Fuzzy match against the vendor master, ignoring legal suffixes. Unknown or suspended vendors are rejected |
| 6 | PO match | Explicit reference, or inference from vendor + amount + description. Wrong-vendor POs are rejected |
| 7 | Duplicates | Same vendor + invoice number (or identical file) is rejected. Same vendor + amount + date is flagged for review |
| 8 | Amounts | Arithmetic, dates, currency, cumulative net vs PO with tolerance bands, high-value threshold |
| 9 | Decide | Worst finding wins (reject > hold > review > approve). Reasons, next step and a drafted email are produced |

Full map with decision branches: [docs/PROCESS_MAP.md](docs/PROCESS_MAP.md). Demo script and likely interview questions: [docs/DEMO_SCRIPT.md](docs/DEMO_SCRIPT.md).

## The edge cases (and why these)

| Sample | Edge case | What it shows |
|---|---|---|
| 03 + 04 | **Split PO**: one PO billed in two invoices | Cumulative tracking across runs; the second invoice has the same amount but is not a false duplicate |
| 06 | **No PO reference** | Infers the PO but never auto-approves an inferred match |
| 07 | **Missing invoice #, date and totals** | Hold plus a specific vendor email, not a generic rejection |
| 08 | **Scanned image, noisy and skewed** | OCR path with a confidence score |
| 05 | **Over PO by 20%** | Rejection with a drafted credit-note request |
| 10 | **Unknown vendor citing another vendor's PO** | Escalated internally instead of replying to the sender |
| 11 | **Duplicate re-sent as a "payment reminder"** | Different file bytes, same invoice number, still caught |
| 02 | **Tax embedded, PO written as "5002", vendor name variant, +1.2%** | Normalisation and tolerance, with the reasoning visible |
| 09 | **High value (≥ 50,000)** | Routed to the finance controller even though everything matches |

## Business rules

All in `data/rules.json`, editable without touching code.

| Rule | Value |
|---|---|
| Auto-approve tolerance (cumulative net over PO) | 2% |
| Review band | 2% to 10%, above that is rejected |
| High-value approval threshold | 50,000 |
| Near-duplicate window | 3 days |
| Stale invoice | 180 days |
| Minimum OCR confidence | 75% |

## Assumptions

- **PO amounts are net (pre-tax).** The invoice's net amount is compared to the PO, and tax is validated separately.
- **Approved and in-review invoices count against a PO.** Held and rejected ones don't, so a corrected resubmission isn't blocked.
- **Numeric dates like 03/04/2026 are read day-first.** Text and ISO dates are unambiguous.
- **An inferred PO always goes to a human.** Paying against the wrong PO costs more than one click.
- **Vendor master, PO data and invoices are synthetic**, generated by `scripts/generate_samples.py`.
- **Emails are drafted, not sent.** They are shown in the UI and can be copied.
- **Extraction is rule-based on purpose:** deterministic, free, explainable. An optional LLM pass (`INVOICE_USE_LLM=1`, `ANTHROPIC_API_KEY`) fills only fields the rules missed and never overrides them. It is off by default.

## Known limits

- Labels with their value on the next line (table-style headers) are not parsed.
- Multi-currency and multi-page line-item tables are not handled.
- Bank-detail change detection against the vendor master is not built; it is the first thing I'd add.
- Tested on the synthetic invoices here, not on a real-world corpus.

## Layout

```
app.py                 Flask server; streams stage events (NDJSON) to the browser
engine/
  pipeline.py          the 9-stage process (a generator, so the UI can show it live)
  extract.py           reading (native / OCR) and field extraction
  checks.py            vendor, PO, duplicate and amount rules
  emailer.py           drafted follow-ups
  db.py                SQLite run history, PO ledger, stats
data/                  rules.json, vendors.json, purchase_orders.csv
sample_invoices/       11 generated PDFs + manifest.json
scripts/               generate_samples.py, test_pipeline.py
templates/, static/    the UI (vanilla JS, no build step)
docs/                  process map, demo script
```

## Sharing the link

Every visitor automatically gets a private demo (a cookie picks their own database), so several people can use the same link at once without affecting each other's duplicate checks or PO balances. Their data is deleted after 24 hours.

## Deploying a live link

The submission needs a live, runnable URL. Any host that runs a Dockerfile works (Render, Railway, Fly.io, Google Cloud Run). The image installs poppler and Tesseract. The SQLite file lives in `/tmp` and resets on redeploy; that is fine for a demo, and **Reset demo data** restores a clean state any time.
